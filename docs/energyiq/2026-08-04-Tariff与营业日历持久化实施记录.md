# EnergyIQ Tariff 与营业日历持久化实施记录

## 1. 当前边界与演进历史

### 1.1 Deep module 首次落地

`packages/metadata/src/energyiq-operational-policy-store.ts` 已建立独立的 Operational Policy 深模块，负责：

- 发布不可变 Tariff Schedule Revision；
- 发布不可变 Operating Calendar Revision；
- 激活供新分析使用的一对 Project Policy 版本；
- 按 Project、Scope、左闭右开 Period 和 Interval Fact 解析 Cost、Operating 与 Standby；
- 为 Published Project Release 提供严格的版本固定入口。

首次深模块提交没有修改 `energy-analysis.ts`、Project Analysis Resolver、API 或 Web Renderer。这是当时正确的历史边界，不再代表当前 Integration 状态。

### 1.2 当前已接通的代码链

当前代码链为：

```text
Admin immutable revisions
  → pending policy binding
  → Project Review & Publish / immutable Template Revision pins
  → ProjectAnalysisResolver binds Published Release versions
  → executeEnergyScopeAnalysis uses release-pinned policy
  → EnergyScopeAnalysis/API DTO
  → Overview Renderer or serialized Saved Analysis
```

| 层 | 当前契约 |
| --- | --- |
| Admin API | Project-scoped GET/POST API 发布不可变 Tariff/Calendar revisions；新版本先进入 pending binding，不提前改写客户 Published Release。 |
| Project publish | `Review & Publish` 在同一发布事务中读取 pending Tariff/Calendar pins，并把它们写入新的 immutable Template Revision。 |
| Resolver | `resolveProjectAnalysis()` 读取最新 Published Project/Template Revision，并用其中的 `tariffScheduleVersion`、`businessCalendarVersion` 覆盖请求上下文；不会从当前 active/pending binding 漂移。 |
| Analysis | `executeEnergyScopeAnalysis()` 从 authoritative scoped interval facts 读取 Scope/Meter series，并以 `policy_source.mode = release-pinned` 调用 Operational Policy evaluator。 |
| API/DTO | Cost、Operating/Standby、版本、币种、timezone、allocation 或结构化 `Unavailable` 进入同一个 `EnergyScopeAnalysis` 合约。 |
| Web | 客户 Overview 的既有 Renderer 显示 Cost + Tariff version，以及 Operating energy、Standby energy、Calendar version、Project timezone；不可用时显示 evaluator 的 reason message。 |
| Saved | Create 与 rerun 都先调用 `ProjectAnalysisResolver`；每个新记录保存当次完整 `analysis_json` 和 Template Revision，读取历史详情时直接反序列化旧 JSON。 |

因此“代码是否接通”的答案已经是“是”；但这不等于真实 Ngee Ann #4 验收完成。自动化 fixture 证明合约和冻结语义，真实 Integration Golden 仍受 #24 的 Meter attachment/navigation/official aggregation route 闭环约束，详见第 8 节。

## 2. 持久化模型

SQLite 新增：

| 表 | 语义 |
| --- | --- |
| `energyiq_tariff_schedule_revisions` | Project 级不可变 Tariff Revision，内部包含 Project/Scope-owned 生效费率条目 |
| `energyiq_operating_calendar_revisions` | Project 级不可变 Calendar Revision，冻结发布时的 Project timezone、周营业时间和日期例外 |
| `energyiq_operational_policy_bindings` | 当前 Project 激活的 Tariff/Calendar 版本对；只用于新分析，不改写历史结果 |

Revision 表拒绝 `UPDATE` 和 `DELETE`。绑定表通过 `(project_id, version_id)` 组合外键同时约束 Project 和版本，不能把 Project B 的版本绑定给 Project A。`version_id` 仍保持全局主键。

## 3. Project/Scope 与生效规则

一个 Revision 是 Project-wide 的不可变集合；集合内每个条目显式拥有以下 Owner 之一：

```ts
type EnergyIqPolicyOwner =
  | { kind: "project" }
  | { kind: "scope"; scope_id: string };
```

解析指定 Scope 时使用“最近 Scope 祖先覆盖 → Project 默认”的优先级。Scope 链必须完整回到当前 Project root；缺父节点、跨 Project 父节点或环依赖直接失败，不能静默把损坏链补成 Project root。

Tariff 使用带时区偏移的生效时刻，并按分析 Period 内实际生效片段计费。每个 Revision 内 Tariff entry id 唯一；相邻片段不会只因 id 相同而合并。若一个 Period 的有效片段出现多个币种，Cost 返回 `TARIFF_CURRENCY_CONFLICT`，不执行隐式换汇。

Operating Calendar 使用 Project timezone 的本地日期、七日周表和日期例外。空时间窗表示明确关闭；缺 Calendar 不等于全天营业或全天关闭。跨营业边界的 Interval Fact 按实际重叠时长分配 Operating/Standby kWh。

## 4. 运行来源必须显式二选一

`evaluateAnalysisPolicy()` 不接受两个独立 optional version。调用方必须选择完整来源：

```ts
type EnergyIqOperationalPolicySource =
  | { mode: "active" }
  | {
      mode: "release-pinned";
      tariff_schedule_version: string;
      business_calendar_version: string;
    };
```

- `active`：同时读取当前 Project 激活的两个版本，供新的未保存分析使用；
- `release-pinned`：Tariff 和 Calendar 必须同时由同一个 Release 上下文提供；
- 缺一个版本、继续传旧式顶层 version 字段或混合两种来源时抛出 `ENERGYIQ_OPERATIONAL_POLICY_SOURCE_INVALID`；
- Release 固定版本不存在时返回对应 `Unavailable`，绝不回退到 active 版本。

这条约束防止历史分析出现“旧 Tariff + 当前 Calendar”或“当前 Tariff + 旧 Calendar”的混合口径。

## 5. API/Web 的 Available 与 Unavailable 合约

### 5.1 Available

`EnergyScopeAnalysis` 与 Web DTO 使用同一 discriminated union：

| 输出 | 必需字段 |
| --- | --- |
| Cost | `status=available`、`amount`、`currency`、`tariffScheduleVersion`、`allocations[]` |
| Cost allocation | `from`、`to`、`ratePerKwh`、`usageKwh`、`cost` |
| Operating/Standby | `status=available`、`operatingKwh`、`standbyKwh`、`usageKwh`、`sharePct`、`timezone`、`businessCalendarVersion` |

Overview Consumption 模块显示金额、实际币种和 Tariff version。Off-hours 模块显示 `Operating energy`、`Standby energy`、Calendar version 和 Project timezone；这些值在 render 时直接来自 API DTO，不在浏览器中重新计算。

### 5.2 Explicit Unavailable

| 场景 | reason code |
| --- | --- |
| 未激活 Tariff | `TARIFF_VERSION_MISSING` |
| Release Tariff 不存在/不归属 Project | `TARIFF_VERSION_NOT_FOUND` |
| Tariff 未覆盖完整 Period | `TARIFF_NOT_EFFECTIVE_FOR_PERIOD` |
| 有效片段币种冲突 | `TARIFF_CURRENCY_CONFLICT` |
| Cost 没有 Interval Fact | `COST_FACTS_UNAVAILABLE` |
| 未激活 Calendar | `OPERATING_CALENDAR_VERSION_MISSING` |
| Release Calendar 不存在/不归属 Project | `OPERATING_CALENDAR_VERSION_NOT_FOUND` |
| Calendar 未覆盖完整 Period | `OPERATING_CALENDAR_NOT_EFFECTIVE_FOR_PERIOD` |
| Operating/Standby 没有 Interval Fact | `OPERATING_FACTS_UNAVAILABLE` |

Unavailable 输出包含 `status=unavailable` 和结构化 `reason.code/reason.message`，并可携带已知的 pinned version。Web 直接展示 reason message，不把缺配置渲染成 0 cost、全天营业、全天关闭或估算值。

没有任何 SGD、费率、营业时间或关闭状态的静默默认值。

## 6. Published Release、Saved serialized result 与 v1→v2

Admin 发布 v2 revision 后，v2 先成为 pending policy；只有新的 Project `Review & Publish` 成功后，Published Template Revision 才固定 v2。之后：

- 新 Overview resolve 和新 Saved Analysis 通过当前 Published Release 使用 v2；
- 已保存的 v1 行继续保留原 `template_revision_id` 和完整 `analysis_json`；历史详情直接读取该 JSON，不按 active/pending policy 重算；
- rerun 调用当前 `ProjectAnalysisResolver`，创建新的 series sequence 并固定当前 Published Release；它不会覆盖旧 v1 行；
- 显式 `release-pinned` v1 仍只解析 v1，即使 Admin 已发布或激活 v2。

自动化已在 serialized seam 证明“新记录变化、旧 `analysis_json` byte-for-byte 不变”。完整 Saved Analysis Save/Reopen 浏览器流程属于 #20，不是 #4 的关闭条件。
