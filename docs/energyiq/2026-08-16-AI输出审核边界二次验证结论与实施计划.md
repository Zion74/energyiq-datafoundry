# 2026-08-16 AI 输出审核边界二次验证结论与实施计划

> 本文是对侧边 Agent 讨论输入的独立二次验证结论。它固定后续红测和修改方向，但在真实 Provider、浏览器和人工价值验收完成前，不把产品效果标记为 accepted。

## 1. 验证基线与结论

二次验证使用：

- 讨论输入：隔离工作树 `energyiq-datafoundry-admin-readiness` 中的《AI 输出审核边界讨论与二次验证请求》，未把其中判断直接当作结论；
- 工作树：`D:\Projects\energyiq-datafoundry-demo-integration`；
- 分支：`codex/stage3-pass3-provider-hotfix`；
- 审查基线：`a59483f`；
- 实现：Layer 2 Section Interpretation v4、Layer 1 Executive v4、Additional Insights identity v16；
- 真实 A→B 证据：A 与 B 均生成独立 Artifact，但旧 Transition 曾把不同 Findings 错判为 `no-material-change`。

**独立结论：部分同意讨论文档，选择 Option 3+。**

同意：

1. Evidence 应约束具体事实，不应要求 Evidence 直接证明所有推断、猜想、反例和低风险实验；
2. 运行时审核与 Stage 3 价值审核必须分工；机器门不负责决定内容是否有启发性；
3. 一个坏句子或 Candidate 应局部失败，不能吞掉有效 sibling、整个 Section 或确定性 Overview；
4. Layer 2 需要复用 Typed Evidence 的 Metric、Entity、Time、Value、Unit 绑定，不能继续只靠“同一个数字在 Evidence 中出现过”；
5. Layer 1 需要 Claim 级来源，不能只凭 Evidence ref 和关键词推断事实等级；
6. A→B 必须完整解释每个 A Finding 和每个 B Finding，不能把模型分类直接当成权威事实。

不同意或需要收窄：

1. **不直接采用任意长度的通用 `claims[]`。** 它会增加填表负担、迁移复杂度和页面机械感；
2. **不一次性删除所有关键词规则。** 关键词可降为 Prompt 提示、诊断或迁移 fallback；安全、Alert 和危险表达扫描仍是硬边界；
3. **不把错误事实降成 speculative 后保留。** 猜想可以没有直接原因 Evidence，但猜想中引用的历史数字、Centre、日期和设备事实仍必须真实；
4. **不为了保留创造性而接受无法拆分的错误前提。** 可独立的有价值角度应保留；依赖错误前提的结论需要 candidate-local repair 或拒绝；
5. **不把 pass@3 机器门变成第二个内容审稿模型。** 新颖性、启发性、清晰度和用户价值继续由盲评与人工批准判断。

## 3. 最终审核边界

### 3.1 运行时审核

必须负责：

- Workspace、Project、Scope、Snapshot、Release、Period、Model、Method、Tool 和 Artifact identity；
- `observation` 中 Metric、Entity、Time、Value、Unit 的直接 Evidence 绑定；
- 历史数字、日期、Centre、设备、Alert、Tool Audit 和租户边界；
- 不安全 Markdown/HTML、Prompt/SQL 泄漏和高风险操作；
- Candidate/句子级 failure isolation；
- 新 revision 只允许 current identity 写入，旧 revision 历史只读。

不负责：

- 判断一个合理猜想是否一定正确；
- 要求推断关系已作为确定性 Fact 存在；
- 仅按 `may/might/could` 决定内容价值；
- 以固定 What/Why/How 模板填满卡片。

### 3.2 内容类型

| 类型 | Evidence 要求 | 允许内容 | 禁止内容 |
| --- | --- | --- | --- |
| Observed | 必须直接证明完整事实 | 已发生的信号、数字、对象、时段 | 借用同值但错误 Metric/对象；未证实原因 |
| Inferred | 必须证明基础信号；关系可由 AI 推导 | 关系、反例、优先级、联系 | 把推导写成已确认事实 |
| Speculative | 至少一个当前 Snapshot Evidence 锚点 | 可能原因、What-if、值得追问的角度 | 伪造历史数字/事故/设备状态 |
| Experiment | Evidence 说明为什么值得尝试 | 低风险、可逆、短周期、带验证指标的尝试 | 把 proposed parameter 冒充历史事实；高风险自动执行 |
| Alert | 严格 Evidence 和 certainty 门 | 确认异常或明确 possible 提示 | 把漏水、短路、火灾等猜想冒充确认事故 |

### 3.3 Stage 3 质量审核

- 机器门：合同、事实、lineage、身份、来源、重复、恢复；
- 盲评：新角度、相关性、清晰度、值得深挖、诚实性、用户价值；
- 人工批准：决定是否成为 publication candidate 或 Method/SOP Proposal；
- 发布：必须绑定批准的 exact attempt，不得新增 Provider Run 或替换内容。

## 4. 方案比较

| 方案 | 做法 | 优点 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 保持 Card + 关键词硬门 | 继续扩正则与专项补丁 | 改动最小 | 误伤、漏判、维护成本持续上升 | 不选 |
| B. 通用 `claims[]` | 所有内容拆成任意 Claim 列表 | 校验最细 | 模型填表、Schema 过重、前端机械化 | 暂不选 |
| C. 自由 Card + 只提取事实 Claim | 只对可识别事实做 Typed binding | 创造性限制最小 | 混合叙事的局部修复边界不稳定 | 可作过渡，不作最终接口 |
| D. Option 3+ | 自然 Card 内保留少量 `observation / angle / experiment` 通道；Key Findings 用 `sourceClaimIds` | 事实精确、角度开放、页面仍自然、可渐进迁移 | 需要合同旋转与历史兼容 | **选择** |

推荐形状：

```ts
{
  title: string;
  observation?: { text: string; evidenceRefs: string[] };
  angle?: {
    text: string;
    epistemicStatus: "inferred" | "speculative";
    anchorEvidenceRefs: string[];
  };
  experiment?: {
    text: string;
    anchorEvidenceRefs: string[];
    parameters: Array<{ value: number; unit: string }>;
  };
}
```

底层结构化不要求前端显示为表格。前端继续呈现自然 Card，并用 `Evidence signal / AI angle / Try this`、epistemic badge、Markdown 强调和 Evidence 下钻组织内容。

Layer 1 不复用 Card 自报的 Evidence 聚合，而使用：

```ts
{
  title: string;
  text: string;
  sourceClaimIds: string[];
  alert?: ...;
}
```

服务端从 exact Section Claim 派生 Section、Evidence 和最终 epistemic status。

## 5. 已确认的 A→B 紧急修复

真实 A/B Transition 暴露了一个独立于“文字是否有价值”的正确性缺口：A 和 B 的 Findings、Evidence、对象均不同，模型却返回 `no-material-change`，旧服务端仍将其保存为 completed。

本分支已按公开 `executeTransition` seam 完成 RED→GREEN：

- 非空 A/B 不允许 `no-material-change`；
- 每个 A Finding 和每个 B Finding 必须恰好被分类一次；
- 重复使用同一 Finding、遗漏其他 Finding 时失败；
- A 消失而 B 为空时允许 `Resolved`；
- A/B 均为空时允许 `No material change`；
- 无关的非空 A/B 应分别返回 `Resolved` 与 `New`，不能隐藏变化；
- 失败归类为 `validation`，保留旧 Transition 作为不可变审计，不改写历史。

自动化证据：Evaluation、Additional Workflow、Metadata Store、API 与公共 Contracts 共 5 个文件 110/110 通过；其中 `preschool-additional-ai-insights-evaluation.test.ts` 26/26 通过；API TypeScript 构建通过。真实 Provider 仍需使用新 idempotency key 重新跑一次，旧错误 Transition 不能作为验收证据。

## 6. RED 测试计划

所有测试必须打公开 production seam，不直接调用私有 regex helper。

### 6.1 Layer 2 Typed Fact Authority

入口：`materializePreschoolSectionResultV4`。

1. Evidence 中存在 `12% total energy`，Claim 写 `12% peak change` → 局部拒绝；
2. 数值相同但 Centre、Metric 或 Period 不同 → 局部拒绝；
3. 数值、Metric、Centre、Period、Unit 全正确 → 接受 observation；
4. 多 Evidence 提出新关系且不含 `may` → 接受并派生 inferred；
5. manual override / cleaning activity 无直接原因 Evidence → 作为 speculative angle 保留；
6. `Centre L 可能用了 7.8 kWh` 且 7.8 不存在 → 拒绝历史事实；
7. `提前 30 分钟关闭` 明确为 experiment parameter → 接受，不要求历史 Evidence 有 30；
8. 错误事实句与独立有价值假设句并存 → 删除错误句、保留假设；
9. 假设依赖错误前提 → 不自动 salvage，candidate-local repair 或拒绝；
10. 一个 Candidate 错误 → 其他 Candidate、Section 和确定性 Overview 不受影响。

### 6.2 Layer 1 精确来源

入口：`createPreschoolExecutiveSynthesizer(...).execute`。

1. 同一 Evidence 同时被 observed 与 inferred Section Claim 使用 → Key Finding 按 `sourceClaimIds` 精确继承，不升级；
2. inferred 关系没有命中 `may/might` → 不仅因措辞拒绝；
3. 一句前半段有 `may`、后半段断言确定原因 → 不得借一个限定词绕过；
4. Cross-Section tool 两个信号 → 可形成 inferred connection；
5. 未引用相关 Section/Tool Claim 的跨 Section 实体 → 局部拒绝；
6. 一个坏 Finding → Summary 和 sibling Findings 保留。

### 6.3 Layer 3 与 A→B

入口：`evaluateAttempt`、`executeTransition`。

1. causal/action 误标 observed，但 observation 与 angle 可分离 → 保留 observation，angle 降级或 repair；
2. B 的 experiment 参数恰好等于 A 历史事实数字 → 不误判 Snapshot 泄漏；
3. B 复述 A 历史数字但 B Evidence 不支持 → 比较前失败；
4. `no-material-change` 但 B 内容/Evidence/epistemic status 改变 → 拒绝；
5. `still-supported` 的 A/B Metric/Entity 不兼容 → 拒绝或要求 Changed/New+Resolved；
6. A/B Findings 全集未恰好覆盖 → 失败；
7. 普通 Overview、Saved A、刷新 → Provider Run 数不增加。

### 6.4 UI

入口：`PreschoolAiSlot`、`OverviewChangeDialog`。

1. Key Finding inferred/speculative → 显示 badge，不强迫正文写固定限定词；
2. A/B 显示具体 `A title → B title`、分类和 Evidence basis，不只显示数量；
3. B AI 未完成 → 确定性 Overview 和指标比较先显示；
4. AI 恢复完成 → 内容原位更新，不推开主要图表或制造页面跳动；
5. Evidence 首层可读，技术 ID 放二级详情。

## 9. 验收门与停止线

依次完成：

1. 每个新增行为先有公开 seam RED；

11. 部署前后重复健康、数据库、权限、Run-count 和回滚门。

停止线：没有真实 Provider、浏览器和人工价值证据时，只能声明代码/合同门通过，不能声明 AI 内容效果或生产部署验收完成。

## 10. 失效条件

出现下列信号时复审 Option 3+：

- 模型长期无法稳定填写三个轻量通道；
- Candidate repair 成本高于重新生成；
- 新项目需要更复杂的 Claim 图而不是线性 Card；
- 实验建议进入自动执行或高风险控制；
- 客户要求完整审计每一个复合 Claim；
- Ngee Ann 第二项目证明 Preschool 的字段边界不可复用。
